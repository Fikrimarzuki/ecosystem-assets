# Momee asset workspace (M1.0e)

This is the **proposed** `momee` project directory, created for the owner's M1.0e asset foundation. A matching `config-ecosystem` registry ID has not been verified. Do not publish or copy an asset on the strength of this directory name alone.

## Boundaries and states

- `incoming/momee/` remains the untouched historical import. A file there is not approved by being imported.
- New editable **Working** assets belong under `projects/momee/source/` when a real source exists. A candidate is an evaluated but unapproved version; keep it under `projects/momee/candidates/` when created. No empty folders are pre-created.
- **Approved** requires an owner decision, a passed visual/technical review and verified rights for the whole lineage. M1.0f puts clearly marked Candidate review renders under `projects/momee/exports/` to test the export contract; that directory alone does not grant production eligibility. The app's development-only preview holds isolated copies under `dev-assets/_pilot/`. A production runtime copy under `public/game/` requires later approval and integration.
- [manifest.json](manifest.json) is the inventory for current shared-workspace files and future Momee production. It records the existing imported Boy candidate without changing its historical state. The app's `assets/production/morning-routine/manifests/calm-chibi-storybook.json` remains the authoritative **historical** record for M0.3–M0.6 inputs, reviews and prior checksums. Do not duplicate those old entries here merely to change paths. Before a future production approval, reconcile the logical ID and lineage against that historical record. The app's eventual runtime manifest lists shipped copies only.
- [recovery.json](recovery.json) is a frozen availability snapshot of the app manifest's missing paths, not a second approval manifest. A matched checksum establishes file identity, not usage rights or readiness.

## Manifest contract

Every actual asset entry has a stable `id`, `category`, one of `Working` / `Candidate` / `Approved`, a source path/format/dimensions/SHA-256, an `exports` list, lineage, rights status and provenance path, approval information, and intended app use. Paths within this repository are relative to its root. A pending export is omitted rather than given a fictitious hash. Every export entry, once produced, has its own path, format, dimensions, SHA-256, tier where relevant, and intended runtime destination. `Approved` is forbidden while rights are unverified or approval is absent.

**Approval contract (M1.0j-C; `scripts/lib/momee-approval.mjs`, tested by `node --test scripts/momee-approval.test.mjs`).** Each entry carries three independent states, plus its workflow `status`:

| Field | Meaning | Values |
| --- | --- | --- |
| `visualAcceptance` | The owner's judgement of a **design direction**; it implies nothing about production use or rights | absent / `null` / `{ state: owner-accepted-visual-direction \| owner-rejected-visual-direction, scope, recordedOn, evidence }` |
| `productionApproval` (legacy alias `approval`) | The owner's approval to **ship** the file in a production runtime | absent / `null` / `{ by, date, scope? }`; if both fields are set they must be identical |
| `rights.status` | Usage-rights verification for the whole lineage | `unverified` / `restricted` / `verified` (`verified` needs `verifiedBy`, `verifiedOn`, `evidence`) |
| `status` | Workflow stage | `Working` / `Candidate` / `Approved` |

The verifier rejects:
- production approval on a non-`Approved` entry;
- `Approved` without production approval, verified rights, an accepted visual direction and exports;
- any production approval of a rejected direction;
- disagreeing `approval` and `productionApproval`;
- malformed states.

Historical entries without the new fields remain valid. The `schemaNote` text in the two M1.0j-B reference entries predates this contract and is kept as history. A revision of an existing Candidate gets a new ID (for example `prop.bedroom.pillow.made.v2`) with `logicalId`, `revision` and `revisionOf`; the earlier entry stays untouched. Studies and review sheets have no exports. Their renders go in an optional `reviewRenders` list (path under `projects/momee/review/`, format, dimensions, SHA-256) and never name a runtime destination.

Run `node scripts/verify-momee.mjs` for structure, IDs, paths, formats, dimensions and file hashes. This uses Node's standard library; it neither generates nor modifies art.

## Source and storage

Keep layered raster originals as `.kra` and vector originals as editable `.svg`. Record source/checksum before deriving versions. Generated originals retain embedded metadata untouched. Never put a private master in an application's public directory. Prefer plain Git for small SVG and approved optimized web exports. The repository currently has LFS patterns for Gateway and Scriptoria only; Momee `.kra`, `.blend` and large PNG files are **not** covered. A proposed policy is: keep sources under 10 MiB in ordinary Git only after a repository-size review; add a project-scoped LFS rule before the first larger `.kra`/`.blend`/`.psd` master, after confirming authenticated remote upload; keep small approved PNG/WebP/SVG exports in ordinary Git. Do not use LFS to bypass provenance or approval review. No Momee LFS rule is installed in M1.0e.

## Export contract

1. **Krita:** paint characters, environments and layered raster parts. Preserve `.kra`; export transparent sprites/interactive states as PNG-32 and opaque backgrounds as WebP (quality around 85–90, visually checked). Keep sRGB color. Check edge colors on dark and light backgrounds; use straight alpha for PNG unless a measured Phaser test requires otherwise.
2. **Inkscape:** author vector icons, learning illustrations, reward symbols and scalable decoration as editable SVG. Keep text and functional controls in application code. Export self-contained plain SVG (`--export-plain-svg`) and optimize/check it with the repository's existing SVG tooling, or transparent PNG at required tiers when Phaser texture handling, visual effects or device testing favors raster. Do not embed external fonts, links or scripts in runtime SVG. Inkscape **1.4.4** is installed and its CLI responds to read-only `--version` and `--help` checks. The CLI lists SVG/PNG export, object/page export, width/height/DPI controls and PNG RGBA modes. No direct Inkscape agent tool was exposed, and no document/export operation was exercised.
3. **Blender:** optional orthographic room/perspective or 2.5D reference studies. Any 2D deliverable must be reviewed against the approved Calm Chibi Storybook master; no 3D runtime dependency is proposed.
4. Name new exports with lowercase ASCII kebab-case and an immutable `vN` plus `@1x`/`@2x` where tiered. For example `rooms/bedroom/pillow-messy.v1.@1x.png`. The same state shares canvas bounds, anchor and pixels-per-world-unit across tiers. `@2x` has exactly twice the width/height of `@1x`. Atlas pages and background tiles stay at or below **2048×2048**.
5. Hash every source and export. Record dimensions, alpha requirement, intended app path (under `apps/web/public/game/calm-chibi-storybook/`) and lineage in the manifest; check output reproducibility where a scripted export is used. Validate visual scale in desktop, phone portrait and phone landscape before approval. A runtime copy is made only in a later integration milestone.

The first exercise is specified in [pillow-pilot.md](pillow-pilot.md) and recorded in [m1.0f-art-pipeline-pilot.md](m1.0f-art-pipeline-pilot.md). Its files are Candidates, with no production asset integration.
