## Tested tool workflow

1. **Krita 5.3.4.1, plugin 1.0.0:** the live bridge created an RGBA/8 document, made two named state groups with three separately editable paint layers each, painted shapes, switched group visibility, exported each @2x PNG and saved a genuine `.kra`. The `.kra` contains Krita's layer XML and paint data, not a PNG renamed to KRA. The bridge writes pixels directly outside Krita's undo history; edits can be made to individual layers, and deleting a layer reverts that part. For a revised state, open the KRA, show one state group, hide the other, paint on the named layers, save as a new version, then export the visible group at 256×192. The @1x tier in this pilot was downsampled with macOS `sips -z 96 128` from the @2x PNG.
2. **Inkscape 1.4.4 CLI:** the editable source uses named Inkscape layers for stem/leaves, petals, and center/highlight. The CLI opened it and wrote a plain SVG, then exported a 128×128 transparent PNG using `--batch-process --export-type=png --export-area-page --export-width=128 --export-height=128`. The final runtime-shape SVG is a compact, self-contained derivative with editor-only attributes removed; `xmllint --noout` validates both files. No direct Inkscape agent tool was exposed. The sandboxed CLI aborted on this Mac; the same installed binary worked with the approved command escalation. Inkscape printed local ColorSync and GTK warnings but exported successfully.
3. **Blender 5.2.3 LTS, add-on 1.8:** the live bridge returned add-on status and the default scene inventory. No scene or art was created because the 2D pilot did not need a 3D reference.

The source paths, checksums, dimensions, per-state group names, intended usage, lineage, rights and approval fields are in `manifest.json`. `node scripts/verify-momee.mjs` checks manifest structure, files and hashes. Regenerate every checksum after a source or export edit; use a new `vN` filename when a Candidate version is replaced. Never rewrite an Approved export in place.

## Development preview and eventual integration

The app's `/dev/art-pipeline-pilot` route is limited to development. It serves isolated Candidate copies from `apps/web/dev-assets/_pilot/m1.0f/`, which Next excludes from traced deployment bundles. It shows both states, source-tier switching, transparency, light and dark edge checks, a size comparison, a mobile-scale study, and the SVG. Its bedroom palette drawing is an illustrative placement study, not the Phaser scene.

The current Phaser `createBed()` builds its pillow as geometric child objects inside a bed container. Loading a candidate sprite there without replacing those objects would draw both pillows. Proper integration needs a later asset-aware bed construction path: choose a tier, preload both textures, map `messy` → `unmade` and `fluffed` → `made`, keep center-origin placement near the current pose and depth, and preserve animation, hit area, story state and reduced-motion behavior. That is a production gameplay change and is outside this pilot.
