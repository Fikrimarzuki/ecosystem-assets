# Asset guidelines

[Repository overview](../README.md) · [Naming conventions](naming-conventions.md)

## Purpose and ownership

**ecosystem-assets owns creative source files and asset production.**
**config-ecosystem owns canonical metadata and approved public asset references.**
**Individual applications own their runtime asset integration.**

* This repository produces the files. It does not decide which project uses which file publicly; that is recorded in `config-ecosystem`.
* `config-ecosystem` stores a path such as `assets/projects/<projectId>/icon.svg` and the file itself. It does not store working files, drafts or concepts.
* An application owns its favicon, manifest, `apple-touch-icon`, SEO and Open Graph setup. It copies the exports it needs and serves them from its own origin. It never links to this repository.

## Private source asset policy

* The repository is private, and editable sources (SVG masters, `.blend`, layered files) stay here.
* Treat exports as the only public form of an asset. A source file is never copied to a public repository or website.
* Do not commit secrets, third-party assets without a licence you can show, screenshots of unapproved or private work, or personal data.
* Keep provenance: when an asset derives from a reference or a purchased/licensed item, say so in a `NOTES.md` beside it.

## Project-first structure

```text
projects/<projectId>/branding/{concepts,source,exports,previews}
shared/branding/<group>/
references/branding/
```

* `<projectId>` is normally the canonical project ID from `config-ecosystem` (camelCase, for example `cv`, `configEcosystem`). Use the same ID the registry uses so a later copy is mechanical. `projects/momee/` is an owner-authorized provisional workspace; confirm its registry ID before publishing a reference there.
* `shared/` holds material that belongs to a family rather than one project, such as the Group 1 palette and notes.
* `references/` holds approved concept sheets and inspiration. References are read-only: never edit or overwrite them; add a new versioned file instead.
* `incoming/<repositoryName>/` can hold an existing private working collection whose project is not yet registered. This is an intake name, not a canonical project ID. Promote it into `projects/<projectId>/` after registration. See [collection imports](collection-imports.md) for Momee and the preserved legacy Gateway and Scriptoria layouts.
* Momee's historical import stays under `incoming/momee/` unchanged. Its [M1.0e workspace](../projects/momee/README.md) describes future Krita raster and Inkscape vector sources. A new workspace does not imply that an imported candidate was approved.

## Source vs export

| | Source | Export |
| --- | --- | --- |
| Folder | `source/` | `exports/` |
| Authored | by hand | by a script, from `source/` |
| Edited | yes | never by hand |
| Examples | `icon.svg`, `tile.svg`, `glyph.svg`, `favicon.svg`, `mono.svg`, `.blend` | `svg/`, `png/`, `favicon/`, `apple/`, `pwa/` |
| Committed | always | when approved |

`concepts/` is exploration and `previews/` is review material (contact sheets, mask tests). Neither is shipped.

Export layout inside `exports/` (generated by `pnpm build:icons`; `pwa/` is a consumer-ready bundle that duplicates files from `png/`):

```text
svg/       icon.svg, favicon.svg
png/       icon-512.png, icon-192.png, icon-maskable-512.png
favicon/   favicon.ico (16/32/48), favicon-32.png, favicon-16.png
apple/     apple-touch-icon.png (180x180, opaque)
pwa/       icon-192.png, icon-512.png, icon-maskable-512.png
```

Disposable build or test output does not belong in `exports/`; it goes to the ignored `checks/` or `.cache/` folders.

## Approved asset workflow

1. **Concept:** explore in `concepts/` or `references/branding/`. Concepts are not production assets; never crop one and ship it.
2. **Source:** draw clean masters in `source/`.
3. **Export:** generate files into `exports/` with `pnpm build:icons`.
4. **Verify:** run `pnpm verify:icons`, then `pnpm contact-sheet` and review `previews/contact-sheet.png` at real sizes on light and dark backgrounds. The script checks structure, not appearance.
   Projects with a wordmark (`projects/<id>/logo/source/wordmark.svg`) also run `pnpm build:logos <id>` and `pnpm verify:logos <id>`, which compose the lockups (`logo/exports/`) and the 1200×630 social image (`social/exports/og-image.png`) from the masters.
5. **Approve:** the owner approves the exports. Commit the approved exports.
6. **Publish references:** copy the approved canonical file into `config-ecosystem/assets/projects/<projectId>/` and add `assets.icon` (or `logo`) to the project record there. That change belongs to `config-ecosystem`, in its own commit.
7. **Integrate:** each application copies the files it needs and wires its own favicon and manifest. That change belongs to the application.

Steps 6 and 7 are separate changes in other repositories and are never made from here.

## Adding a new project

1. Confirm the canonical project ID in `config-ecosystem/config/projects/` before publication. Momee's provisional workspace is an explicit owner-approved exception for preparation.
2. Create `projects/<projectId>/` and only the subfolders you have files for. Do not pre-create empty trees.
3. Add the first asset under the matching `branding/` subfolder (or the folder for its kind).
4. Add a short `NOTES.md` when ownership, licence or provenance is not obvious.

Projects that need no dedicated artwork get no folder.

## Adding new branding assets

1. Put exploration in `projects/<projectId>/branding/concepts/`, named with a version (`name-v01.png`).
2. Put masters in `source/` using the names in [naming-conventions.md](naming-conventions.md).
3. Follow the production plan for icons: 512x512 canvas, `viewBox="0 0 512 512"`, filled shapes only (no text, fonts, emoji, filters or external references), a 3:1 glyph-to-background contrast, an 80% safe area for maskable and Apple icons, and a separately simplified small-size master for favicons.
4. Generate exports; do not hand-edit them.
5. For a family asset, use `shared/branding/<group>/`.

## Large binary assets

* Most branding sources are small text (SVG) and need no special handling. Keep SVG as text and diff-friendly.
* Large binaries (`.blend`, `.psd`, `.kra`, `.fbx`, audio masters, video) bloat history and cannot be merged. Keep them out of normal Git history.
* Raster exports are small for icons but can grow for illustrations. Do not track "every image" in LFS; decide per kind.
* Keep `.blend1`/`.blend2` backup files and autosaves out of the repository (they are ignored).
* Compress or downsize before committing exports; commit one approved version, not every iteration.

### Git LFS

**Status as of the 2026-10-23 collection import:** Git LFS 3.7.1 is available on the import machine. [`.gitattributes`](../.gitattributes) now tracks imported Gateway and Scriptoria `.blend` sources, plus Gateway `.fbx`, `.npz` and `.webm` files. Small web models and raster images stay in ordinary Git. See [collection imports](collection-imports.md#binary-storage).

Every clone that commits or pushes these files needs Git LFS installed and `git lfs install --local` run in the repository. Fetch binary contents with `git lfs pull` after cloning. For future asset kinds, extend `.gitattributes` before the first large binary is committed. Possible additional patterns, to adopt only when needed:

```gitattributes
*.psd    filter=lfs diff=lfs merge=lfs -text
*.kra    filter=lfs diff=lfs merge=lfs -text
*.wav    filter=lfs diff=lfs merge=lfs -text
*.mp4    filter=lfs diff=lfs merge=lfs -text
```

Consider carefully before adding: `.png`/`.webp` (small icons should stay in plain Git), `.glb`/`.gltf` (approved web exports are usually small), and `.mp3`/`.ogg`. Existing files are never migrated automatically; adopting LFS for committed files needs `git lfs migrate` and a history decision.
